data.trackedData is empty on every real save until scanning writes into it, so the Gradebook has nothing to draw. These build a fake three-week shiur — attendance, homework, two count items and a capped pass — for checking that the grid renders, filters and prints. Sample data lives here, never in app.html.

Busy-state sample (layout testing)

A shiur that has been running a while: 15 students, 40+ log entries, mixed activities and point values, and several deliberately long names so the recent-scans strip is as wide as it realistically gets. Restore this into the app to test any layout that behaves differently once there is real history in it.

Why this exists. Several layout bugs have now been fine in one data state and broken in the other — the scan strip (stubby input when empty / wrapped row when busy), the seating chart (arranged vs never-arranged), and the class sheet (one class vs a full roster). A fresh install is the easy state to test and it only ever shows you half the bugs. Sample data lives here, never in app.html.

Open the app in a known state

Writes a sample straight into localStorage and opens app.html on it — no download, no restore, no clicking through Backup & Restore. For checking layouts that only misbehave in one data state.

Your own data is protected. Before the first seed, whatever is really in localStorage is copied aside, and Put my real data back returns it. Seeded saves are tagged, so seeding twice never overwrites that copy with sample data.

Must be served over http (e.g. http://localhost:3000/test-migration.html). Opened as a file:// page these do nothing useful — the harness and the app do not share a localStorage, so the app would open on whatever it already had.
