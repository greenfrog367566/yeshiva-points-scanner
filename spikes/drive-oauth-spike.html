1 · Setup (do this once)

  1. Create a throwaway project at console.cloud.google.com.
  2. Enable the Google Drive API (APIs & Services → Library → Drive API).
  3. OAuth consent screen → External. Add scope https://www.googleapis.com/auth/drive.file — it will be listed as non-sensitive, which is the whole point: no verification review. Add yourself as a test user. Leave it in testing mode.
  4. Credentials → Create OAuth client ID → Web application. This page uses a redirect flow, so both of these must be registered exactly as shown — copy them from here rather than typing them:
    No client secret is needed — the browser token flow doesn't use one.
  5. Paste the client ID into CLIENT_ID at the top of this file's script, or into the box below to try it without editing:

The client ID is not a secret — it identifies the project and authorises nothing on its own, the same property Firebase API keys have. The redirect URI must match character for character, which is why this page computes it for you instead of asking you to guess it.

3 · Run the steps in order

The step that matters is ⑤, and then ⑥ followed by ③. Everything before them only proves the API works, which was never in doubt. ⑤ asks whether the app can quietly get a new token an hour into a lesson without interrupting the rebbi. ⑥ then kills the token for real, so ③ has to recover from a genuine 401 rather than a simulated one — that is the exact moment a backup would silently stop working in a classroom. Run the whole thing again on a shared/logged-out Chromebook; a laptop where you are permanently signed into Google is the easy case and will tell you almost nothing.

⑦ exists to disambiguate a failure in ⑤, and only matters if ⑤ failed. interaction_required has two very different causes with opposite consequences. Either (a) the Google session genuinely cannot issue a token without the rebbi doing something — in which case automatic backup is impossible — or (b) the session is perfectly alive and only the hidden frame was blocked, because an iframe to accounts.google.com is a third-party context and Chrome restricts third-party cookies. ⑦ runs the identical prompt=none request as a top-level redirect instead of in a frame. If it comes back with a token and no visible sign-in, the cause was (b): re-auth needs no typing, only a page bounce that costs the app its in-memory state. That is a far better position than (a) and points at a different design.

5 · Findings — run 2026-08-09

Both halves work. Sign-in, folder creation, a 509-byte write in ~1.1s, read-back and in-place update all succeeded first time, with no SDK and no external script. Token lifetime came back as 3599s, exactly as documented — and it renews silently, so that hour is not a ceiling on anything.

Silent re-auth works — and an earlier version of this section said it did not. The first run reported interaction_required from every silent route, because this page was not sending a login_hint. Google's account chooser had appeared during sign-in and the auth URL carried authuser=unknown: more than one Google account in this browser, no default. prompt=none cannot succeed while Google is guessing which account is meant. Once ⑧ captured the address and every request named it, ⑤ returned a fresh token with no UI at all, and ⑥ → ③ recovered from a genuine 401 twice, invisibly, finishing the write in 1819 ms. The testing-mode confound is moot — all of that happened with the client still unverified.

  • Does silent re-auth work on your own laptop? yes — invisible, with login_hint
  • Does it work on a shared Chromebook, signed out of Google? still untested — and the question has sharpened: not does renewal work, but how often is he signed out of Google entirely, and what happens that morning?
  • login_hint is mandatory, not a nicety. A rebbi with a personal and a school Google account in one browser is the normal case; without the hint his backup silently stops renewing. ⑧ gets the address from Drive's own about.get — no scope beyond drive.file.
  • The 60 minutes cannot be lengthened, and no longer needs to be. Access-token lifetime is fixed for user OAuth, and a refresh token is unavailable to a browser-only app — Google requires a client secret and, unlike most providers, PKCE cannot substitute. Renewal rides the Google session instead, which is enough.
  • What can still fail: signed out, session expired, consent revoked. A failed renewal has to be a visible state, not a quiet stop — the staleness nudge stays the backstop.
  • Design consequence: never persist the access token (this page keeps it in memory only), and persist pending work before the interactive path, which redirects and discards in-memory state. The silent path is frame-based and preserves it.
